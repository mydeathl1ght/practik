# Практическая работа №6: Обработка ошибок и защита соединений

## Что сделано

1. В `app.py` добавлена обработка ошибок при добавлении задачи через `try/except/finally`.
2. При ошибке SQLite вызывается `rollback()`, ошибка выводится в консоль, а пользователю показывается понятное сообщение.
3. Функция `fetch_all_tasks()` тоже обрабатывает ошибки и возвращает пустой список, если чтение не получилось.
4. Соединение с базой закрывается в `finally`.
5. Добавлен простой шаблон `templates/index.html`, чтобы проект можно было запустить отдельно.

## Как запустить

Нужен Python 3 и Flask.

```bash
python -m pip install flask
python app.py
```

Открой в браузере `http://127.0.0.1:5000`.

При первом запуске автоматически создаётся файл `app.db` и таблица `tasks`.

## Проверка обработки ошибки

В `app.py` временно найди запрос:

```python
cursor.execute(
    "INSERT INTO tasks (title) VALUES (?)",
    (title,)
)
```

И замени `(title,)` на `(None,)`. После отправки формы SQLite вызовет ошибку ограничения `NOT NULL`. Приложение должно показать сообщение «Не удалось сохранить задачу. Попробуйте ещё раз.», а соединение закроется благодаря `finally`.

После проверки обязательно верни `(None,)` обратно на `(title,)`.

## Контрольные вопросы

### 1. Почему `conn.close()` нельзя оставлять просто в конце функции, а нужно помещать в `finally`?
Потому что при ошибке выполнение может прерваться до строки `close()`. Блок `finally` выполняется в любом случае, поэтому соединение не останется открытым.

### 2. Что делает `conn.rollback()` и в каком случае он вызывается?
`rollback()` отменяет изменения текущей транзакции, которые ещё не были зафиксированы. В этой работе он вызывается в `except`, если произошла ошибка SQLite при добавлении задачи.

### 3. Почему `conn` нужно открывать до `try`, а не внутри?
Чтобы переменная `conn` точно была создана до выполнения `finally`. Если открыть соединение внутри `try` и само открытие завершится ошибкой, в `finally` может оказаться нечего закрывать.

### 4. Чем `except sqlite3.Error` лучше, чем `except:` без указания типа?
Он ловит ошибки, связанные с SQLite, и не перехватывает без разбора другие исключения, например остановку программы через Ctrl+C. Так проще понять, какую ошибку мы обрабатываем.

### 5. Что произойдёт с данными, если `execute` прошёл, а `commit` упал?
Изменения могут остаться незавершёнными в текущей транзакции. Если ошибка обработана и вызван `rollback()`, эти изменения отменятся. Если откат не сделать, нельзя рассчитывать на корректное состояние транзакции.

### 6. Зачем в веб-приложении возвращать пользователю понятное сообщение вместо стектрейса?
Стектрейс выглядит непонятно для обычного пользователя и может раскрыть технические подробности приложения. Лучше показать короткое сообщение, а подробности ошибки оставить в консоли или журнале.

### 7. Как проверить, что `rollback` действительно откатил транзакцию?
Временно передать в `INSERT` значение `None` вместо названия задачи. SQLite выдаст ошибку `NOT NULL`. После этого проверить список задач: новая запись не должна появиться. Затем вернуть обычное значение `(title,)`.

## Вывод

В этой работе я добавил обработку ошибок для операций с базой данных. Теперь при ошибке изменения откатываются, соединение закрывается, а пользователь видит понятное сообщение вместо технической ошибки.
